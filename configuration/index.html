    ⚙️ Configuration System

    The project’s configuration system is a three‑layered, type‑safe mechanism built on Pydantic that ensures all settings are valid, consistent, and easy to customize.

    1. Configuration Layers & Loading Order

    Base configuration (conf/config.yaml)

    • General, project‑wide defaults (I/O paths, caching, Ray, GPUs, etc.).
    • Metric‑specific overrides (conf/model/*.yaml)
    • One file per metric (CLIP, BLIP2, ImageReward, TIFA) to tweak only that metric’s fields.
    • Command‑line overrides
    • Instant updates via --section.key=value, requiring no file edits.

    🗂️ Base Configuration (conf/config.yaml)

    # Core parameters
input:
  path: data/raw/challenge_set.csv         # Input CSV path
  chunk_size: 10000                        #  Process input csv in chunks

output:
  path: data/processed/challenge_set_${model.type}.csv          # Output CSV - Dynamic naming

app:
  cache_dir: data/cache         # Local image caching
  ttl_days: 7
  max_connections: 100.         # Parallel downloads
  output_columns:               # Output CSV structure
    - url
    - caption
    - score
  use_ray: true                 # use distributed computing
  ray_workers: 8                # number of workers for ray
  annoy_index_name: annoy-clip  


# Model configuration
model: ...

    Note the ${model.type} placeholder—your output filename will automatically include clip, blip2, etc.

    🗂️ Metric-Specific Configurations

    Located underconf/model/, each YAML defines only that metric’s extra fields and defaults:

    conf/model/
├── clip.yaml          # CLIP scoring model
├── blip2.yaml         # BLIP-2 (itm/itc)
├── image_reward.yaml  # ImageReward preference model
└── tifa.yaml          # TIFA VQA scoring

    Examples:

    • BLIP2-itc (blip2.yaml):
    type: blip2
mode: itc
model_name: blip2_image_text_matching
precision: fp32
batch_size: 8
variant: pretrain
    • TIFA score (tifa.yaml):
    type: tifa
question_generation_model: tifa-benchmark/llama2_tifa_question_generation
unifiedqa_model: allenai/unifiedqa-v2-t5-large-1363200
vqa_model: blip2-flant5xl
precision: fp16

    📌 Command-Line Overrides

    Any parameter—base or metric—can be overridden without editing files:

    python main.py --model=clip --model.precision=fp16 --app.max_connections=32
    • Format: --section.key=value
    • Works for any field in your loaded config hierarchy.

    📌 Validation & Safety

    All configs are validated against Pydantic schemas in src/config/config_schema.py. This guarantees:

    • Required fields are present
    • Types (int, str, Literal) match
    • Constraints (e.g. output.path must include ${model.type}) hold

    If validation fails, you’ll see a clear error at startup rather than a runtime crash.

    Examples:

    ImageRewardConfig

    class ImageRewardConfig(BaseModel):
    """ImageReward model configuration."""
    type: Literal["image_reward"]
    model_name: str
    batch_size: int = 16
    precision: Literal["fp16", "fp32"] = "fp32"

    BLip2Config

    class BLIP2Config(BaseModel):
    """BLIP-2 model configuration."""
    type: Literal["blip2"]
    model_name: str
    mode: str
    precision: Literal["fp16", "fp32"] = "fp32"
    batch_size: int = 8
    variant: Literal["pretrain", "coco"] = "pretrain"

    Initialization Flow

    • Load & validate base + metric configs
    • Apply CLI overrides
    • Instantiate the registered model class with the validated config
    • Error if no matching @register_model(...) is found

    This ensures you can’t accidentally request an unsupported metric or supply invalid params.

    📌 Model Configuration and Creation

    Each model has a corresponding configuration schema (e.g., ClipConfig, BLIP2Config) and is registered using a decorator:

    Example:

    @register_model(ImageRewardConfig)  # Links config schema to model class
class ImageRewardModel:
    def __init__(self, config: ClipConfig):  # Guaranteed valid config
        self.precision = config.precision  # fp16/fp32
        self.tokenizer = AutoTokenizer.from_pretrained(config.model_name)
        ...

    Initialization Flow:

    1. Validate config against config (e.g. ImageRewardConfig) schema
    2. Instantiate model (e.g. ImageRewardModel) with validated parameters
    3. Reject unregistered models to prevent runtime failures
